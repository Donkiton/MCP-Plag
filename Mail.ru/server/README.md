# Mail.ru MCP 0.4.0

Python HTTP MCP-сервер с OAuth/PKCE, IMAP/SMTP Mail.ru и интерфейсом подключения ящиков. Текущая версия предоставляет **31 команду**. Исходники Python в `mailru_mcp/` совпадают с сохранённым снимком развёрнутого релиза 0.4.0 по SHA-256. Для многопользовательской конфигурации требуется `cryptography`; зависимости указаны в `requirements.txt`.

## Локальные тесты

```sh
python -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests -q -p no:cacheprovider
```

На Windows используйте `.venv/Scripts/python.exe`. Тесты поднимают локальный HTTP-сервер, создают временные базы и подменяют почтовые операции; реальные пароли и подключение ящиков для них не нужны.

Проверено на Python 3.12.14: **192 теста и 20 subtest прошли**. Полный комплект запускается через pytest: часть проверок не входит в `unittest discover`.

## Новые команды и поведение

| Команды | Назначение |
| --- | --- |
| `list_drafts`, `read_draft`, `update_draft`, `send_draft` | Полный цикл сохранённого черновика с проверкой его версии |
| `reply_message`, `forward_message` | Ответ, ответ всем и пересылка; по умолчанию создают черновик, `send=true` требует явного запроса отправки |
| `read_messages`, `read_thread` | Чтение до 20 сообщений и связанной переписки из разных папок без изменения признака прочтения |
| `move_messages`, `archive_messages`, `mark_messages_read` | Действия над точным списком UID; свыше 50 сообщений выполняются фоновой задачей |

В `create_draft` и `prepare_send` доступны `bcc`, `html_body` и `attachments`. Вложение передаётся как base64 с именем файла либо как ссылка на MIME-часть конкретного письма. Произвольные URL и пути файлов сервера не принимаются. Лимиты: 20 файлов, 5 МБ на файл, 8 МБ суммарно, 12 МБ итоговое MIME-письмо. Чтение вложения ограничено 2 МБ.

Для изменения и отправки черновика нужны `uid_validity` и `message_fingerprint` из `read_draft`. Для пакетных изменений нужна текущая `uid_validity` исходной папки. Новая копия черновика проверяется до удаления старого UID. SMTP-результат и сохранение авторской копии в «Отправленных» отражаются отдельно; неопределённый результат не повторяется автоматически.

Отправка сохранённой версии резервируется в таблице `draft_deliveries` до SMTP. Квитанция сохраняется после перезапуска и предотвращает повторную отправку той же версии. Сохраняйте базу при обновлениях. Если возвращён `action_id`, опрашивайте `action_status` до конечного результата; внутренние блоки фоновой задачи не требуют повторных запросов пользователя.

## Новая установка на Ubuntu/Debian

Скопируйте содержимое этой папки в `/tmp/mailru-mcp`. `deploy/install.sh` устанавливает исходники и systemd unit, но **не создаёт Python-окружение и не запускает службу**. Он отказывается перезаписывать существующую установку. Выполните от root:

```sh
bash /tmp/mailru-mcp/deploy/install.sh
python3 -m venv /opt/mailru-mcp/venv
/opt/mailru-mcp/venv/bin/python -m pip install -r /tmp/mailru-mcp/requirements.txt
```

Настройте `/etc/mailru-mcp.env` по `.env.example`, права `root:root 0600`. Для текущего режима оставьте `MULTI_ACCOUNT=1`, задайте публичный HTTPS origin и сгенерируйте `MAIL_CREDENTIAL_KEY` непосредственно на сервере:

```sh
/opt/mailru-mcp/venv/bin/python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Сохраните ключ только в закрытом файле настроек. Он нужен для расшифровки существующих подключений; при переносе рабочей установки его нельзя менять без отдельной миграции. Ящики подключаются через веб-интерфейс с отдельным паролем приложения Mail.ru.

`deploy/configure.py` — прежний интерактивный помощник для **одноящичного** режима: он задаёт `MAILRU_EMAIL`, `MAILRU_APP_PASSWORD` и `MCP_LOGIN_PASSWORD`. Для него нужно использовать `MULTI_ACCOUNT=0`; текущую конфигурацию с несколькими ящиками он не заменяет.

## HTTPS и ресурсы интерфейса

- `deploy/nginx-vdsina.conf` — конфигурация на основе действующего vhost без временных проверочных значений. В этой установке публичный 443 занят stream-маршрутизатором, а HTTP TLS vhost слушает `127.0.0.1:8443`.
- `deploy/prepare-sni.py` — помощник для конкретной существующей схемы SNI; изучите его перед использованием.
- `deploy/nginx-site.example.conf` и `deploy/Caddyfile.example` — альтернативные шаблоны для отдельного HTTPS-прокси.
- `deploy/cert-renew-hook.sh` — обработчик обновления сертификатов.

При переносе замените домен, пути сертификатов и порты согласно инфраструктуре. Закрытых ключей сертификатов в репозитории нет. Не запускайте второй прокси поверх уже занятого порта.

Важно сохранить правила nginx для `/login.css`, `/login.js`, `/login-icon.png`, `/roboto.ttf`, а также `/cancel` и `/icon.png`. Приложение хранит все эти ресурсы в `mailru_mcp/`, включая `roboto-OFL.txt` с лицензией шрифта.

Оба шаблона nginx используют `client_max_body_size 12m`, чтобы пропускать запросы с вложениями. При обновлении замените прежнее ограничение 250–260 КБ и проверьте лимиты вышестоящего прокси. Сервер ограничивает HTTP-тело отдельно; ограничения MIME и base64 тоже применяются.

После настройки HTTPS и закрытого файла окружения:

```sh
systemctl enable --now mailru-mcp
curl --fail http://127.0.0.1:8765/health
```

Ожидаются `status=ok`, `version=0.4.0`, `tool_count=31`. Endpoint MCP — `/mcp`; OAuth discovery — `/.well-known/oauth-authorization-server`. Для подключения используется HTTPS, сервер слушает только loopback. После обновления существующего App синхронизируйте список инструментов: 12 команд чтения и 19 команд записи. `deploy/preflight.py` проверяет доступность TLS IMAP/SMTP без входа. `deploy/check-mailbox.py` предназначен для отдельной проверки прежнего одноящичного режима и требует настроенного окружения.

## Существующая установка и данные

Эта папка — исходники и шаблоны, а не полная резервная копия подключённых аккаунтов. Рабочий `/etc/mailru-mcp.env` и `/var/lib/mailru-mcp/state.sqlite3` сохраняются отдельно в защищённом хранилище. Обновление существующей службы требует отдельной резервной копии и процедуры; `install.sh` для обновлений не предназначен.

Подготовка данного снимка не изменяла и не перезапускала рабочую службу.
